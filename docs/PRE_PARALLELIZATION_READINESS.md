# Pre-parallelization readiness

The master gate document for this workstream: fixing the co-primary
`rule_based`/`rule_based_monotone` registration collision, locking the
statistics protocol, producing a figure/table manifest cross-checked against
the logging schema, wiring `random_search` for every primary-matrix arm,
mechanizing the `fast_dev`/`primary_matrix` config-profile distinction,
resolving the `hidden_channels` wiring gap, distinguishing ablation-within-arm
from cross-arm comparisons, and confirming tree hygiene. See the explicit
**NOT covered by this document** section at the end -- this is a
wiring/documentation/validation gate, not a launch sign-off.

Full per-arm `describe()` output (all fields, including read-only constants
like `min_rules`/`max_rules`/`condition_types`), for either profile, is
reproducible via:
```
python -c "
import dataclasses
from evodevo.experiments.benchmark import BenchmarkConfig, resolve_configs, _resolved_arm_kwargs, PRIMARY_MATRIX
from evodevo.core.factors import extract_factors
from evodevo.encoders import get_encoder

bconfig = BenchmarkConfig.from_yaml('evodevo/experiments/configs/benchmark.yaml')
# bconfig = dataclasses.replace(bconfig, profile=PRIMARY_MATRIX)  # to inspect the other profile
resolved = resolve_configs(bconfig)
for arm in bconfig.resolved_arms():
    config = resolved[(arm.arm_id, 'Walker-v0')]
    kwargs = _resolved_arm_kwargs(bconfig, arm)
    factors, remaining = extract_factors(kwargs, seed=config.seed)
    enc = get_encoder(arm.encoder, factors=factors, grid_shape=config.grid_shape, **remaining)
    print(arm.arm_id, 'ppo_timesteps=', config.ppo_timesteps, 'population_size=', config.population_size, 'eval_budget=', config.eval_budget)
    print(' ', enc.describe())
"
```

## 2. Current experimental matrix

**Arms**: `direct`, `nca`, `rule_based`, `rule_based_monotone` (4; the
`rule_based`/`rule_based_monotone` co-primary pair registered as distinct,
non-colliding arms by Part 1 of this change).
**Strategies (ablation axis)**: `ea`, `random_search` (2; P7's
representational-prior-vs-search-contribution control, wired for all four
arms by Part 4).
**Tasks**: `Walker-v0` (1) -- **this is intentional, not an oversight.** The
matrix is deliberately single-task at this gate: adding a second, harder
task is explicitly the NEXT step after this workstream (see the "NOT
covered" section below), not part of it. Every mechanism this change
introduces (`ArmSpec`/`resolved_arms()`, `enumerate_planned_comparisons`,
the logging-schema additions) is verified task-agnostic (Part 3's Appendix)
specifically so that next step requires no further rework here.
**Seeds**: 5 per arm/strategy/task cell (`seeds: [0,1,2,3,4]` in
`benchmark.yaml`), per the P4/N-series floor (`docs/analysis-protocol.md`
Sec 5).

Total matrix size: `4 arms x 2 strategies x 1 task x 5 seeds = 40` planned
runs.

## 3. Statistical protocol: locked and validated

`docs/analysis-protocol.md` locks, with justification: Mann-Whitney U as the
primary test, Vargha-Delaney A12 as the effect size reported alongside every
p-value, Holm-Bonferroni correction over the actual planned-comparison
family (`m=10` for the current matrix, computed explicitly by
`evodevo/analysis/stats_protocol.py::enumerate_planned_comparisons`, not
estimated), median+IQR convergence curves (and `budget_curves.py` updated to
match, since it was previously mean+min/max), the 5-seed floor's honest
power disclosure, and sentinel-fitness-included handling consistent with the
Invalid-genome policy.

**Both validations in `results/STATS_PROTOCOL_VALIDATION.md` PASS**:
1. Synthetic Gaussian recovery: A12 at n=5000/group recovers the analytic
   value to within 0.006; averaged over 4000 n=5 trials, mean A12 is within
   2 SE of the analytic value (unbiased at this project's real seed floor).
   Under a simulated null (m=10, n=5/group, 3000 trials), the uncorrected
   family-wise error rate (0.4257) is far above alpha=0.05 while the
   Holm-corrected rate (0.0000) controls it, exactly as the protocol
   document asserts.
2. Dry run on a freshly-generated 4-arm surrogate dataset
   (`results/runs/strategy_comparison_v2/`, built via the real, current
   `benchmark.yaml` config path; the original 3-arm
   `results/runs/strategy_comparison/` predates `rule_based_monotone`'s
   registration and is kept as-is) ran end-to-end with no errors, producing
   a correctly-labelled 10-comparison table -- including
   `rule_based/ea vs rule_based_monotone/ea` correctly labelled
   `ablation_within_arm`, distinct from every other pair's `cross_arm`
   label (see &sect;3a below).

**3a. `cross_arm` vs. `ablation_within_arm`**: `stats_protocol.py::
enumerate_planned_comparisons` now derives a distinct `ablation_within_arm`
kind (vs. `cross_arm`) for any two arms sharing a base encoder registry
entry -- generically, from an explicit `arm_base_encoder` map, never
hardcoded by name (`docs/decisions.md`'s "Distinguish ablation-within-arm
from cross-arm comparisons" row; verified to generalise to a hypothetical
future encoder's own ablation variant, not just `rule_based`). This matters
for interpretation: `rule_based` vs. `rule_based_monotone` is an ablation
question (does monotone's termination guarantee cost task performance
within one encoding), categorically different from `direct` vs. `nca` (a
representation-choice question) -- `docs/analysis-protocol.md` Sec 3 and
`docs/paper-manifest.md`'s Table 4 both document why conflating the two
labels would misrepresent what a significant result licenses concluding.

## 4. Figure/table manifest: cross-checked against the logging schema

`docs/paper-manifest.md` lists every figure/table the final report will
contain (numbering, title, caption skeleton, exact axes/columns, arms/tasks
covered, no data), cross-checked against
`evodevo/evolution/eval_bookkeeping.py::EvaluationTracker` (the single
shared per-evaluation/per-generation logger both `ea.py` and
`random_search.py` use).

**Schema gaps found and fixed** (additive JSONL fields only, confirmed
task-agnostic by an explicit grep, see the manifest's Appendix):
1. `generation_unique_valid_bodies` -- per-generation morphology-diversity
   proxy (distinct valid `body_hash` count within that generation's own
   batch); previously unavailable (only cumulative/per-individual data
   existed).
2. `generation_invalid_reason_counts` + `generation_size` -- per-generation-
   only (non-cumulative) invalid-reason breakdown; previously only a
   cumulative-to-date version existed (`evals_invalid_reason_counts`).

**Gap explicitly NOT fixed, and why that's correct**: the exact-cycle-vs-
chaos comparison figure needs no new per-run logging -- it is computed
entirely from `depth_study.py`/`dynamics_classification.py`/
`horizon_extension.py`'s own offline, standalone sampling, never from
`run_log.jsonl`/`generation_log.jsonl`.

## 5b. `ppo_timesteps` and `hidden_channels`: audited with git-history evidence, not assumed

**`ppo_timesteps=5000`** (`docs/decisions.md`'s "Mechanize the
already-disclosed ppo_timesteps gap" row): confirmed via `git log --follow
-p`/`git log --all -S"ppo_timesteps"` to have been present, unchanged, since
this project's very first commit -- but NOT an un-surfaced leftover: the
original roadmap docs and this log's own "Direct-encoding real-PPO baseline
budget" row already disclosed it as a pipeline-validation-scale placeholder
and named EvoGym's own >1e6-timestep recommendation as the real target. What
was missing was a MECHANISM, not a disclosure -- now provided by the
`fast_dev`/`primary_matrix` profiles in &sect;1.

**`hidden_channels`** (`docs/decisions.md`'s "Audit hidden_channels=3..."
row): `resolved_config.py::PRIMARY.hidden_channels` was already `0`,
correctly matching the last-recorded decision ("Hidden channel count (H) --
final re-resolution": "DROP H to 0") -- NOT a regression in the resolved
value itself. The real bug was that `benchmark.py::
_BUILTIN_ARM_DEFAULT_KWARGS` had no `"nca"` entry, so the real benchmark
path fell through to `ExperimentFactors.hidden_channels`'s own stale default
(`3`), exactly the class of gap already fixed for rule_based's readout
policy but never extended to NCA's one shared-factor-layer field -- now
fixed and tested
(`tests/experiments/test_benchmark.py::test_real_benchmark_yaml_wires_nca_resolved_hidden_channels`).
Downstream artifacts were checked one by one: the capacity study and
`results/nca/ARCHITECTURE_DELTA.md` were already correctly measured at H=0;
`results/mutation/MUTATION_CALIBRATION.md` was genuinely stale (committed
once, at the very first P5 run, and never regenerated despite two later
re-runs' numbers being cited in `docs/decisions.md`) and has been
regenerated fresh, reproducing the third re-run's cited numbers exactly
(D*=2.5000, nca `mutation_sigma`=0.0305).

## NOT covered by this document

This is a wiring/documentation/validation gate. It explicitly does **not**
cover, and must not be read as covering:

- **Parallelised execution** of the benchmark matrix (multiple runs
  concurrently) -- not implemented, not even partially/as a stub, per this
  task's own MUST NOT list.
- **A second, harder task** -- the matrix above is deliberately single-task
  (`Walker-v0`); adding a second task is the next workstream, not this one.
- **The pre-flight wall-clock projection on the lab machine** -- `estimate_wall_clock()`
  measures cost in THIS environment; a real projection for the actual lab
  hardware the full matrix will run on has not been performed here.
- **Lab PC hardware specs** -- not gathered or assumed anywhere in this
  document.
- **A literature sweep** -- no related-work/citation survey was performed as
  part of this gate.
- **`population_size` and `eval_budget` (and `offspring_size`, the
  generation count) for the `primary_matrix` profile -- OPEN, pending the
  pre-flight wall-clock projection and an explicit scoping decision.** No
  number is set anywhere for these under `primary_matrix`
  (`PRIMARY_MATRIX_OPEN_FIELDS`), and none should be inferred from this
  document, from &sect;1's table, or from `fast_dev`'s `15`/`15`/`300` --
  those are `fast_dev`'s own values, not a default for the real matrix. Any
  attempt to launch a REAL run under `primary_matrix` without these
  explicitly supplied fails loudly (`OpenProfileDecisionError`) rather than
  silently proceeding at a guessed or inherited value.

Nothing in this document authorizes launching the full real-PPO matrix on
lab hardware; it only certifies that the arm-registration, statistics, and
logging-schema groundwork for doing so is in place and tested.
